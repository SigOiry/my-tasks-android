# Mobile API v1

All `/api/*` endpoints require the existing `Authorization: Bearer <mobile token>` or a validated opaque browser session. Cookie-authenticated unsafe requests additionally require the configured exact Origin and `X-CSRF-Token`; bearer clients are unchanged. See `WEB.md` for login, expiry, CSRF and logout. Token comes from server-only secret file, never Hermes host dashboard token. HTTPS via reverse proxy required off localhost. `/health` returns only `{"status":"ok"}`.

- `GET /download/my-tasks.apk` is public and serves only server/public/my-tasks.apk; 404 until parent publishes an APK. Never includes token.
- `GET /api/tasks` → `{tasks:[Task], today:"YYYY-MM-DD", week_end:"YYYY-MM-DD", sync:{...}}`. Includes deleted/completed tasks; client groups/filter/sorts priority high/medium/low then due date (null last).
- `GET /api/tasks/{id}` → Task.
- `POST /api/tasks` → 201 Task. JSON editable fields: title (required), description, status, priority, due_date (YYYY-MM-DD or null), project (string or null), notes.
- `PATCH /api/tasks/{id}` → Task; JSON `{revision:"64hex", ...editable fields}`.
- `DELETE /api/tasks/{id}` → soft-deleted Task; JSON `{revision:"64hex"}`.
- `POST /api/tasks/{id}/restore` → Task; JSON `{revision:"64hex"}`.
- `POST /api/tasks/{id}/updates/read` → Task; JSON `{token:Task.notification.token}`. Never ack without displayed exact token.
- `GET /api/events?after=0&limit=100` → `{events:[{id:integer,task_id:string,kind:"created"|"updated"|"deleted"|"restored",token:"64hex",created_at:string}],cursor:integer,has_more:boolean,notification_tracking:boolean}`. Initial poll establishes quiet baseline; no historic flood. Events persist across restarts; poll even if task list unchanged. Metadata only; fetch current task for notification text. `notification_tracking` is true exactly when canonical dashboard notification metadata has been explicitly initialized, not when the SQLite feed baseline exists. Only an explicit false permits fallback alerts for created/updated/restored events even if current task unread is false; missing/unknown tracking never permits fallback. With tracking true, notify only current unread tasks, never already-read tasks. Suppress currently deleted/missing tasks in every mode. Baseline stays quiet and no poll initializes/acknowledges canonical notifications. Meaningful task changes and delete/restore only; ack/timestamp/notes do not alert. Feed detects canonical changes at poll time, not a real-time push service. Events can coalesce between polls. Cursor is last delivered event, preserve it only after notification processing. Native periodic polling is best effort, OS scheduling applies.
- `POST /api/chat` JSON `{task_id:string,message:string,mode:"question"|"email_draft",history?:[{role:"user"|"assistant",content:string}]}` → `{reply:string,mode:string,task_id:string}`. Synchronous; client read timeout at least 180 seconds (Android uses 200,000 ms), with proxy upstream/read timeout greater than 200 seconds (e.g. 210). Provider retries/fallback may extend the 90-second per-request timeout; neither the client deadline nor disconnect cancels provider work. Timeout/network/interruption copy must warn that the original provider request may still be running. Never automatically replay chat; manual re-send may duplicate provider work. The installed configured auxiliary API exposes no per-call retry/fallback limit, so no global/shared provider configuration is modified and no hard end-to-end deadline is claimed. No tools or email send. Task/evidence injected as untrusted context. History max 12 messages; current message and each history content max 8000 Unicode codepoints. Server body cap is 65,536 bytes, including all JSON framing and UTF-8/escaping overhead. Android sends the exact pure-helper serialization at <=60,000 UTF-8 bytes, evicting oldest whole history turns until it fits (omitting out-of-schema history turns). Current message is validated independently, never shortened or trimmed. HTTP 413 means change/shorten the request, not retry the identical payload; Android blocks identical resubmission in the current activity after 413. `503` means unavailable real provider, never fabricated answer.

Task = canonical fields plus notes, deleted, revision, source_accounts, source_links, notification:{unread,token,headline,summary,updated_at}. Status enum inbox/todo/in_progress/waiting/completed/cancelled; priority high/medium/low. Error JSON `{detail:...}`: 401 unauthenticated, 404 missing, 409 stale revision/notification or duplicate identity, 413 request body too large, 422 invalid, 503 store/provider unavailable. No arbitrary provider/model/URL/tool selection by client.
