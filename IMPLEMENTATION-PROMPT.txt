2. COMMIT TO A COHERENT iOS-STYLE PRESENTATION

Use pearl/cool-neutral light mode, graphite dark mode, clear charcoal/white type, thin inset separators, circular completion controls, grouped content, refined value rows, anchored contextual menus and floating glass capsules. Use one fine-line icon family and one restrained Hermes identity. Retain licensed Inter or use the Android system font with precise weights and a consistent hierarchy.

The result should clearly read as an iOS-inspired productivity app throughout Tasks, details, forms, messaging, sign-in and settings. Do not mix that direction with unrelated default Material styling on individual routes.

Put real supported backdrop treatment on navigation, utility controls, selected capsules, contextual surfaces, sheet rims and composers. Keep reading text, forms and message bubbles sharp on stable surfaces. On capable devices, visibly sampled/blurred background content, quiet tint, a fine highlight and restrained elevation should establish the material. A near-opaque gradient renamed glass is not an acceptable primary implementation. Avoid thick outlines, heavy embossed shadows, moving wallpaper, neon and multiple glass layers behind prose.

Use Android-owned system bars, back behavior, keyboard, accessibility and permission flows. Do not draw fake iOS status bars/home indicators or package Apple's proprietary fonts. Verify contrast on the final material composite and honor reduced motion/transparency.

3. MAKE SCREEN SPACE USEFUL

On an ordinary compact viewport around 390 x 844dp, excluding OS bars:
- Keep title, scopes and filtering/sorting ordinarily within about 120-128dp total.
- Use a clear 28-32sp main Tasks heading that can collapse when scrolling or height is constrained.
- Aim for seven ordinary task rows across two groups, normally at least six visible useful rows. Let wrapping, accessibility type and shorter windows expand/reflow appropriately.
- Use roughly 16sp task titles, 13-14sp context, 16-20dp page gutters, aligned 8/12/16dp spacing and rows around 60-72dp at default text size.
- Keep native hit targets at least 48dp. Never meet density goals by clipping text, shrinking targets or hiding essential actions.
- Put the project once in its group header. Do not repeat it below every task, show full descriptions in the list or make a large raised card for each row.
- Use a small amount of current context, not a greeting, statistics dashboard, badge collection or permanent technical status paragraphs.
- Expose less-used filters through a clear menu/sheet instead of displaying every option permanently.
- Keep the final row reachable above floating controls.
- On compact details/edit and full-screen chat, hide the global tab capsule. Use a clear back route and one relevant action/composer area, not stacked footers.
- Let short forms and empty states end naturally. Do not invent content just to fill a screen.

Tasks and Discussions are the two global destinations. Settings is a utility. Projects are scopes within Tasks.

4. TASKS, DETAILS AND HERMES UPDATES

Tasks is the default destination. Preserve project grouping/filtering, priority/date sorting, search and the existing Active/Today/Week/All/Trash capabilities in a concise hierarchy.

An ordinary task tap opens beautifully composed details: title, description, project, priority, due date, status, notes and supported sources/activity. Edit exposes all user-editable fields using labelled compact groups, useful selectors and reachable Save/Cancel. Preserve revision checks, unsaved drafts and conflict resolution. Identities/provenance/bookkeeping stay managed.

Long press anchors a useful menu for supported status, priority, project, Edit and recoverable Trash actions. Include an accessible overflow equivalent. Completion-control taps are distinct from opening a row.

When Hermes produces a genuinely new canonical update, show a persistent New update dot/label and two subtle blue accent/edge breaths, roughly 2.0-2.6 seconds per cycle, then settle. Do not animate task text opacity or whole-row size. Polling, row recycling, sorting and revisiting must not replay the same update animation. Batch multiple arrivals and stop offscreen/background effects.

Tapping an unread task first opens the update sheet: concise Context, What's new and optional supplied next steps. Use actual snapshot-bound prose. Offer explicit Mark reviewed, Open task and Ask Hermes paths. Dismissing/opening/animation completion does not acknowledge. Submit only the exact displayed token and clear unread only after confirmation. A newer update during review/acknowledgement remains reviewable. Preserve safe summary rendering and keep source navigation in ordinary details.

5. MAKE HERMES CHAT FEEL LIKE MESSAGING

Use clear incoming/outgoing groups, readable bubbles, quiet timestamps/date separators, selectable text and a polished multiline composer above the IME. Keep top chrome compact and task context visible without a bulky header. No console-style history or a separate form card around every message.

Autoscroll only near the bottom or after my send. Otherwise preserve reading position and offer jump-to-latest. Loading older messages preserves the visible anchor. Preserve drafts through task/thread navigation and folding. Replies must remain in their originating request/thread.

Keep durable admission, idempotency and recovery. Distinguish unsent, accepted, responding and failed/interrupted states. Do not automatically replay ambiguous requests. Show streaming, voice, receipts and tool activity only when genuinely supported.

Discussions provides saved task/free threads, concise previews, timestamps, New conversation and supported rename/archive/reopen/history controls. Search wording must match its actual scope.

Free chat supports general conversation and planning new requests/projects. Where supported, show a structured DRAFT proposal with explicit review/apply through canonical APIs, followed by confirmed success. Do not fake a created project, invent a separate database or widen Hermes's email/calendar/tool authority to make a preview appear functional.

6. DESIGN FOR MY FOLDABLE

Use measured current window dimensions, not a hardcoded phone name. When unfolded, provide a compact glass navigation rail, a useful list master pane and a readable detail/chat pane. A composer belongs to the active chat pane only. Avoid both stretched phone screens and tiny desktop panels.

Pixel_Fold must retain task selection, selected thread, list position and drafts while folding/unfolding, rotating or resizing. Let available width and minimum usable pane sizes determine the transition. Respect actual occlusions and keyboard height. Test both folded and unfolded states; final Samsung-specific behavior is also checked on a physical phone when available.
