# v1.6.2 shared implementation contract

All routes use existing /api authentication, native sessions, Origin/CSRF, no-store, strict bounded schemas. Never send real mail during QA. New state uses a dedicated private `email.sqlite` sibling of conversations.sqlite; mobile_api preflights its identity before constructors. One backend owner, no competing draft mirrors. Canonical task fields are unchanged.

## Source and draft API

- `GET /api/tasks/{task_id}/email-sources?update_token=TOKEN` -> `{sources:[Source], ambiguous:boolean, reason:string|null}`. Token optional for task details, exact token required for update entry. Reject stale supplied token with409. Opaque IDs are validated against task membership server-side. Legacy accumulated references are labelled historical/candidate, never asserted to be exact causal origins. Multiple/ambiguous rows always require explicit selection. Thread-only refs expand bounded exact-message candidates; exclude duplicates, never silently choose latest/self-sent.
- `GET /api/tasks/{task_id}/email-sources/{source_id}` -> `{source:Source,thread:[{sender,subject,date,body}]}` for authenticated citation/source panels; validate membership, no draft creation or acknowledgement.
- **Shared source identity:** `email_providers.source_id(task_id, reference)` returns `'src_'+sha256((task_id+'\0'+reference).encode('utf-8')).hexdigest()[:32]`. Server revalidates every ID against task membership. Chat metadata for saved emails uses this as `resource_id`, includes `task_id`, and never puts raw references into public links. A list may expand a thread ref into exact-message choices with IDs based on those exact validated refs.
- `POST /api/email/drafts` `{request_id,task_id,source_id,update_token:null|string,reply_all:false}` -> Draft. Idempotent creation/reopen returns the same unsent draft for its source/mode; no arbitrary provider/account/recipient/host/path input.
- `GET /api/email/drafts/{id}` -> Draft.
- `PATCH /api/email/drafts/{id}` `{expected_revision,body}` -> Draft. CAS;409 never destroys local input.
- `POST /api/email/drafts/{id}/refresh-context` `{expected_revision,reply_all?:boolean}` -> Draft. Explicitly refresh task/source/thread and current update token while preserving body; changing Reply/Reply all is explicit here. If source unavailable, block send with a useful reason.
- `DELETE /api/email/drafts/{id}` `{expected_revision}` -> `{discarded:true}`. Explicit UI confirmation; never delete sent/uncertain receipts.

`Source`: `{id,kind:"email",provider:"gmail"|"nantes",account_label,sender,subject,date,excerpt,available:boolean,replyable:boolean,reason:null|string,origin:"trigger"|"historical"|"candidate"}`. No credentials/raw opaque provider internals. Metadata/body is private to authenticated owner. Unsupported/unavailable refs produce useful rows, not invented source URLs. Read-only source resolution must not acknowledge task updates or mailbox flags.

`Draft`: `{id,task_id,source_id,update_token,revision,status:"draft"|"sending"|"sent"|"uncertain",from:string,to:[string],cc:[string],subject,body,reply_all:boolean,source:Source,thread:[{sender,subject,date,body}],ai_messages:[{id,role,content,proposal?:Proposal}],latest_ai_request:Job|null,can_send:boolean,send_result:null|object,error:null|string}`. Missing optional fields handled defensively. Plain text is authoritative; multiline native/browser selection and spelling are supported without introducing an unsafe rich-text editor.

## Contextual AI and controlled changes

- `POST /api/email/drafts/{id}/assist` `{request_id,expected_revision,intent:"draft"|"improve"|"discuss"|"edit",instruction}` -> Job (202 appropriate). Tool-free configured provider only. Persist identity/input before work; exact replay never repeats model calls. Current body, bounded exact source/thread, task/update context and relevant prior draft chat only. Source content is untrusted data, never instructions. No public research, mail tools or unrelated mailbox access.
- `GET /api/email/drafts/{id}/assist/{request_id}` -> Job.
- `POST /api/email/drafts/{id}/proposals/{proposal_id}/apply` `{expected_revision}` -> Draft. Require both current and proposal base revision; stale proposal409 preserves newer user writing.
- `POST /api/email/drafts/{id}/proposals/{proposal_id}/dismiss` `{}` -> `{dismissed:true}`.
- `Job`: `{id,status:"queued"|"running"|"succeeded"|"failed"|"interrupted",error:null|string,message?:object,proposal?:Proposal}`.
- `Proposal`: `{id,base_revision,body,kind:"draft"|"improve"|"edit",status?:string}`. All generated changes are previews until explicit Apply. Discussion alone never modifies body. Ask AI history is draft-bound and persists after closing.

## Explicit sending

- `POST /api/email/drafts/{id}/preview` `{expected_revision}` -> `{confirmation_id,draft_revision,from,to,cc,subject,body,source,context_changed:boolean,notice?:string}`. Fresh exact-account source/thread headers; review includes current context. Store short-lived confirmation bound to immutable revision/content/recipient/thread fingerprint. If fresh source/thread/task context differs from the persisted draft, return409 **without creating confirmation**; require explicit refresh-context (body preserved, revision bumped) and human review of that now-visible context first.
- `POST /api/email/drafts/{id}/send` `{request_id,expected_revision,confirmation_id,confirmed:true}` -> Draft. Durable single submission; explicit human confirmation only. Refetch/validate origin/context before sending; stale preview returns409. Bound worker and persist attempt before provider call. Poll Draft while sending. Duplicate clicks/replays do not send twice; restart or ambiguous SMTP result becomes uncertain, never automatically retried.
- `POST /api/email/drafts/{id}/reconcile` `{}` -> Draft. Read-only sent-item reconciliation; no resend. Confirm success only with provider receipt/readback. Preserve sent/uncertain receipts.
- Preserve exact provider account, Reply-To, Reply/Reply-all selection, original subject and References chain/In-Reply-To; Gmail supplies threadId. Exclude own verified identities, never infer Bcc. Outgoing mail remains available to normal existing semantic sync; do not mark task completed or mutate canonical fields just because mail was sent. Expose the durable sent receipt/activity in the task composer.
